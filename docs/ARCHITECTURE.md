# Архитектура GG Email

## 1. Цели и ограничения

| Цель | Решение |
|---|---|
| Стабильный локальный кеш | SQLite (WAL) вместо mbox/JSON-файлов; кеш полностью восстановим с сервера |
| Умеренное потребление ресурсов | один процесс Electron, виртуализированный список, тела писем по требованию, сжатие, лимиты кеша |
| Много аккаунтов без путаницы | отдельные папки/цвета, «Все входящие», независимые синхронизаторы |
| Обновления без прав администратора | NSIS per-user + `electron-updater` (дифференциальные загрузки) |
| Управление через GPO | ADMX/ADML, чтение `HKLM`/`HKCU\SOFTWARE\Policies\GG Email`, горячее применение |
| Gmail/Яндекс/mailcow | пресеты, autoconfig, OAuth2 (PKCE) и пароли приложений |

│              │             ├── imap.ts (ImapFlow, IDLE)            │
│              │             ├── smtp.ts (nodemailer)                │
│              │             ├── mime.ts (mailparser + вложения)     │
│              │             └── oauth.ts (PKCE)                     │
│              ├── db/ (node:sqlite, репозитории, миграции)          │
│              ├── policy.ts (реестр GPO → PolicyState)              │

Ключевые файлы:

| Файл | Ответственность |
|---|---|
| `src/main/index.ts` | жизненный цикл приложения, окно, протокол `kurier-att://`, меню |
| `src/main/app-context.ts` | composition root: репозитории, синхронизаторы, фоновые задачи |
| `src/main/mail/sync.ts` | алгоритм синхронизации на аккаунт, очередь операций, отправка |
| `src/main/mail/imap.ts` | подключение ImapFlow, TLS/STARTTLS, конвертация флагов |
| `src/main/db/repos.ts` | SQL-запросы, маппинг строк, флаги, поиск |
| `src/main/policy.ts` | чтение реестра (`reg.exe`), нормализация, наблюдатель |
| `src/shared/policy-catalog.json` | единственный источник правды для политик и ADMX |

## 2.1 Веб-режим

Тот же main-код работает и в браузере: `npm run web` собирает `out/web/server.cjs`,
который поднимает HTTP-сервер на `127.0.0.1:4173`.

- Обработчики API вынесены в `createApiHandlers()` и не зависят от транспорта:
  Electron регистрирует их через `ipcMain`, веб-сервер — через `POST /api/call`.
- События (`sync-status`, `messages-changed`, …) идут в браузер через SSE `/api/events`.
- Вместо Electron API подключается шим `src/web/electron-shim.ts`: пути, `shell`,
  `safeStorage` (AES-256-GCM вместо DPAPI), заглушки окна и диалогов.
- Доступ защищён токеном: сервер печатает ссылку `/?token=…`, токен проверяется для
  API и вложений, страница отдаётся только с валидным токеном или cookie.
- Boot-конфигурация вынесена в `/api/boot.js`, потому что CSP запрещает inline-скрипты.

Ограничения веб-режима: один профиль на пользователя, нет автообновления и
системных диалогов сохранения (вложения скачиваются браузером), сервер слушает
только localhost, если явно не задан `GGEMAIL_HOST`.
## 3. Модель данных

```
accounts ──< folders ──< messages ──< attachments
                   └──< pending_ops (офлайн-операции)
accounts ──< outbox (неотправленные письма)
```

Особенности:

- `messages.id` — sha1(`folderId|uid`), поэтому уникален в пределах папки; при перемещении
  письма строка обновляется вместе с вложениями и записью FTS.
- Тела писем хранятся сжатыми (`*_gz BLOB`), заголовки — всегда. `body_state = 1`
  означает, что тело загружено.
- `folders.uid_validity`, `uid_next`, `highest_modseq` — состояние синхронизации.
- `message_fts` (FTS5, `unicode61 remove_diacritics 2`) индексирует тему, отправителя,
  получателей и текст; при отсутствии FTS5 автоматически включается LIKE-поиск.

Миграции: `PRAGMA user_version` + массив `MIGRATIONS` в `src/main/db/schema.ts`.
Схема версионируется, обновление выполняется в транзакции.

## 4. Синхронизация

### 4.1 Обнаружение папок

`client.list()` → для каждой папки определяется роль:

1. special-use флаг (`\Inbox`, `\Sent`, `\Drafts`, `\Trash`, `\Junk`, `\Archive`);
2. атрибуты `\All`, `\Flagged`;
3. имя папки, включая русские («Отправленные», «Черновики», «Корзина», «Спам», «Архив»);
4. `INBOX` без специальных признаков.

Синхронизируются роли `inbox, sent, drafts, trash, junk, archive`. Прочие папки
доступны в дереве и синхронизируются по клику. Это осознанное решение: не тянуть
гигабайты «All Mail» и архивов при первом запуске.

### 4.2 Инкрементальный проход

```
open(folder)
uidValidity' = mailbox.uidValidity
if uidValidity' != folder.uidValidity:
    удалить кеш папки, uidNext = 1          # сервер пересоздал UID-пространство

lastUid = MAX(uid) в кеше
serverNext = mailbox.uidNext
from = lastUid > 0 ? lastUid + 1 : max(1, serverNext - 200)   # первичная загрузка — 200 писем

while from < serverNext and fetched < 2000:
    from..to = батч ≤ 250 UID
    FETCH (UID, ENVELOPE, FLAGS, SIZE, INTERNALDATE, BODYSTRUCTURE [, MODSEQ])
    UPSERT messages; индексировать в FTS
    from = to + 1

STATUS (MESSAGES, UNSEEN) → счётчики папки
```

- Флаги обновляются событиями `flags` (если сервер поддерживает CONDSTORE — с `changedSince`).
- `expunge`/`exists` от IDLE планируют синхронизацию папки с дебаунсом 1.5 с.
- Раз в 15 минут для папок ≤ 50 000 писем выполняется сверка `FETCH 1:* (UID)`:
  письма, удалённые другим клиентом, убираются из кеша.
- Ошибка соединения → `offline`, переподключение с экспоненциальной задержкой
  (2 с → 5 мин), состояние уходит в UI.

### 4.3 Тела и вложения

Тело загружается при открытии письма (`FETCH uid BODY[]`), разбирается `mailparser`,
вложения сразу пишутся на диск, в SQLite остаются метаданные. Это даёт:

- мгновенный список при старте (только заголовки, ~100–200 байт на письмо после сжатия);
- контролируемый размер кеша (лимит из политики);
- возможность повторно скачать тело, если его вытеснили.

### 4.4 Офлайн-операции

Флаги и перемещения применяются оптимистично в UI. При ошибке сети операция
сохраняется в `pending_ops` и повторяется после переподключения (до 5 попыток).
Копия отправленного письма, которую не удалось положить в «Отправленные»,
ставится в очередь `append`.

### 4.5 Отправка

1. `mailparser`/`MailComposer` собирает MIME (text + html + вложения, base64).
2. `nodemailer` отправляет по SMTP (TLS/STARTTLS, таймауты, `verify` в мастере).
3. Копия кладётся в папку роли `sent` через IMAP `APPEND` (или в очередь при сбое).
4. При ошибке SMTP письмо попадает в `outbox` с текстом ошибки.

## 5. Производительность и кеш

| Мера | Эффект |
|---|---|
| WAL + `synchronous=NORMAL` | быстрые записи без блокировок чтения |
| gzip тел (уровень 6) | HTML-письма сжимаются в 4–8 раз |
| заголовки вместо тел | список из 10 000 писем — единицы мегабайт |
| `@tanstack/react-virtual` | в DOM ~20 строк независимо от размера папки |
| FTS5 | поиск по 100 тыс. писем за десятки миллисекунд |
| лимит кеша (`MaxCacheSizeMb`) | вытеснение самых старых тел, заголовки остаются |
| срок хранения (`CacheRetentionDays`) | автоочистка тел старше N дней |
| один IMAP-соединение на аккаунт + мьютекс | нет шторма переподключений |

## 6. Безопасность

- **Секреты.** Пароли и refresh-токены — в `secrets.bin`, зашифрованном DPAPI
  (`safeStorage.encryptString`). В SQLite секретов нет. Файл пишется атомарно,
  права 0600 (на Windows — ACL профиля).
- **Транспорт.** TLS 1.2+, проверка сертификата (`rejectUnauthorized: true`),
  STARTTLS для 587. Политика `RequireTls` запрещает учётные записи без шифрования.
- **HTML-письма.** DOMPurify (белый список тегов/атрибутов) → sandboxed `<iframe>`
  с CSP `default-src 'none'; script-src 'none'; frame-src 'none'`. Внешние картинки
  заменяются, пока пользователь не разрешит их для конкретного письма.
- **Вложения.** Встроенные картинки отдаются по схеме `kurier-att://` (main читает
  только файлы из кеша). Опасные расширения блокируются политикой на открытие и
  сохранение — и в UI, и в main-процессе.
- **IPC.** Каждый обработчик проверяет, что вызов пришёл из `file://` или локального
  dev-сервера; `nodeIntegration` выключен, `contextIsolation` включён.
- **OAuth2.** Authorization Code + PKCE, loopback-redirect на `127.0.0.1`, state
  проверяется, refresh-токен хранится в DPAPI.

## 7. Политики

`src/shared/policy-catalog.json` описывает 22 политики: ключ, имя значения реестра,
тип, значение по умолчанию, категорию, тексты ru/en, диапазоны и варианты enum.

```
policy-catalog.json ──┬──> policy.ts (типы, значения по умолчанию, нормализация)
                      ├──> tools/gen-admx.mjs ──> GGEmail.admx + adml (ru/en) + README
                      └──> UI (форматирование значений, блокировки)
```

- Чтение: `reg query HKLM\...\GG Email /s` и `HKCU\...`, декодирование OEM-кодировки,
  `REG_DWORD/QWORD/SZ/EXPAND_SZ/MULTI_SZ`.
- Приоритет: машинная политика > пользовательская > локальные настройки > значения
  по умолчанию.
- Некорректное значение не применяется, попадает в `PolicyState.errors` и в
  диагностику; клиент продолжает работать.
- Наблюдатель опрашивает реестр каждые 2 минуты (GPO применяется при входе и по
  расписанию), изменения применяются без перезапуска.
- Для тестов поддерживается `GGEMAIL_POLICY_FILE` — JSON-файл вместо реестра.

## 8. Обновления

- Установщик NSIS: `perMachine: false`, `requestedExecutionLevel: asInvoker`,
  каталог `%LOCALAPPDATA%\Programs\GG Email`. Тихая установка — `/S`.
- `electron-updater` с generic-провайдером: `latest.yml` + `*.blockmap`, поэтому
  скачивается только разница между версиями.
- Политики: режим (`auto/notify/disabled`), канал (`stable/beta/internal`), интервал
  проверки, отсрочка установки на N дней, собственный URL сервера обновлений.
- Подпись кода не обязательна для работы, но рекомендуется: без неё SmartScreen
  показывает предупреждение при установке.

## 9. Отказоустойчивость

| Сбой | Поведение |
|---|---|
| Обрыв сети | статус `offline`, backoff, повтор операций из `pending_ops` |
| Битый кеш | «Очистить кеш» в настройках: удаление писем/вложений, повторная загрузка |
| Смена UIDVALIDITY | автоматический сброс папки |
| Ошибка SMTP | письмо в `outbox`, ошибка в тосте |
| Некорректная политика | значение игнорируется, остальное применяется |
| Падение при старте | логи `%APPDATA%\GG Email\logs\kurier.log`, понятный экран ошибки |

## 10. Ограничения и развитие

- Нет календаря, адресной книги, S/MIME и PGP.
- Черновики только серверные; локальное автосохранение — следующий шаг.
- Поиск по телам идёт только по загруженным письмам (ленивая индексация).
- `PreconfiguredAccounts` пока не используется мастером.
- Возможные направления: MSIX/Intune, общий кеш для RDS, шаблоны писем, правила фильтрации.
